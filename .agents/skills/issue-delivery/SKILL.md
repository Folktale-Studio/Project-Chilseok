# 칠석 이슈 브랜치와 로컬 커밋

## 구현 시작

1. 승인된 이슈의 초안 번호(`Bxx`), 확인된 GitHub 번호, 선행 이슈를 `production/backlog-draft.md`와 GitHub에서 확인한다. `Bxx`와 GitHub 번호는 실제 매핑을 사용한다. 선행 작업이 현재 기준에 포함됐는지 Git 커밋도 확인한다.
2. `git status --short --branch`와 스테이징 영역을 확인한다. 승인된 이슈의 브랜치가 있으면 재사용하고, 없으면 `codex/bNN-짧은-영문-작업명` 형식으로 만든다. 기본 브랜치에 선행 코드가 있으면 거기서 시작한다. 선행 코드가 로컬 기능 브랜치에만 있으면 그 브랜치의 확인된 커밋을 기준으로 삼고 보고에 기준 브랜치를 적는다.
3. 기존 작업을 보존할 수 있는 전환 방식을 선택한다. 브랜치 전환이 기존 파일과 충돌하거나 선행 코드의 기준이 불명확하면 상태와 필요한 결정을 보고한다. 선행 코드의 머지는 별도 승인을 따른다.

## 검증 뒤 로컬 커밋

1. 작업의 품질 게이트와 확인 가능한 완료 조건을 검증하고 `docs/progress.md`에 기록한다. 게이트가 FAIL 또는 INCOMPLETE면 원인을 해결하고 다시 검증한다. 판정이 남아 있으면 변경을 보존하고 미검증 상태를 보고한다.
2. `git diff --cached`로 커밋에 현재 이슈의 변경만 들어가는지 확인한다. 공유 파일은 해당 이슈의 부분만 담고, 기존에 스테이징된 다른 변경은 보존한다. Unity가 생성한 `.meta`는 해당 에셋과 함께 담는다. `git diff --cached --check`가 생성된 `.meta`의 빈 값 뒤 공백을 보고하면 Unity 원본을 보존하고, 그 외 경고는 커밋 전에 확인한다.
3. 커밋 메시지에 `Bxx`를 넣어 이슈 한 건을 로컬 커밋으로 남긴다. 커밋 뒤 브랜치명, 짧은 커밋 해시, 테스트 결과와 남은 조건을 보고한다.

## PR 머지로 이슈 닫기

1. 푸시·PR 생성·머지는 `AGENTS.md`의 승인 범위를 따른다. 승인된 PR을 준비할 때 GitHub에서 저장소의 기본 브랜치와 PR 대상 브랜치를 확인하고, PR 변경에 해당 이슈의 완료 조건을 충족하는 구현과 검증 근거가 들어가는지 확인한다.
2. PR이 기본 브랜치를 대상으로 하고 이슈의 완료 조건을 충족하면 본문에 검증 결과, 접근 가능한 근거와 `Closes #번호`를 적는다. 선행 기능 브랜치 대상 PR이나 일부 조건만 충족한 PR에는 `관련 이슈 #번호`로 참조한다. PR 대상을 기본 브랜치로 변경할 때 변경 범위와 완료 조건을 다시 확인한 뒤 자동 닫기 연결을 갱신한다. [GitHub 이슈와 PR 연결](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)
3. 머지 승인 전에 함께 닫힐 이슈 번호를 알린다. 승인된 머지 뒤 GitHub에서 이슈가 닫혔는지 확인한다. 열려 있으면 PR 대상 브랜치와 저장소의 자동 닫기 설정을 확인한다. 수동으로 닫아야 하는 예외는 `AGENTS.md`의 승인 범위를 따른다.
