description: "기능 하나를 계획 → 승인 → 구현 → 품질 게이트 순서로 처리한다."
---

사용자가 준 인자(작업 설명, `design/` 노트 경로 또는 `docs/progress.md` 단계 이름)를 바탕으로 작업을 처리한다. 메인 세션에서 직접 한다. 여러 파일에 걸친 큰 구현에는 Codex의 `gameplay-programmer`를, 셰이더·Timeline·임포트에는 `unity-specialist`를 호출할 수 있다.

1. **파악**: `docs/progress.md`에서 이 작업이 속한 단계를 찾고, 관련 기획 노트(`design/`)와 코드를 필요한 부분만 읽는다.
2. **계획**: 바꿀 파일 목록, 새 클래스의 목적·관계(합성/집약)·근거, 테스트 계획(EditMode 테스트 이름), 모르는 점을 짧게 제시하고 승인을 받는다.
3. **브랜치 준비**는 GitHub 이슈 또는 백로그 `Bxx` 구현 계획이 승인된 경우 `$issue-delivery`의 시작 절차를 따라 한다. 스킬 적용과 로컬 Git 작업은 승인된 계획에 포함된다.
4. **구현**은 승인된 범위에서 한다. 순수 로직은 테스트와 함께 쓴다. 범위 밖 문제는 "후속 작업"으로 적기만 한다.
5. **검증**은 Codex의 `unity-quality-gate` 에이전트를 호출해 한다. INCOMPLETE면 이유와 사람이 할 일을 적는다. 가능하면 사람에게 Play 모드 확인을 요청한다.
6. **기록**은 `docs/progress.md`의 해당 항목을 갱신하고, "AI가 한 일 / 사람이 한 일"을 한 줄씩 남긴다.
7. **로컬 커밋**은 이슈 작업의 품질 게이트와 확인 가능한 완료 조건이 통과하면 `$issue-delivery`의 커밋 절차를 따라 한다.
8. **보고**에는 브랜치·커밋, 변경 파일, Unity에서 사용자가 할 일, 게이트 결과, 미검증 항목과 **사람이 조정할 값**(항목·컴포넌트와 필드·기본값·범위)을 적는다. 해당 값이 있으면 `production/tuning.md`의 행을 함께 안내한다.
9. **작업 기록**은 `$notion-log` 스킬의 기록 기준을 따른다.
